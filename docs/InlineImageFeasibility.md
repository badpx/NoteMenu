# 图文顺序保存：独立可行性验证

验证日期：2026-09-20，macOS 26.6.2（25G83）。仅验证独立样本，未修改应用保存实现或现行规范。**最新结论见末节：原生 NSAppleScript 后台图文混排已验证成功，应优先沿用后台通道。**

## 样本与方法

使用 AppKit 生成 RTFD，依次包含：24pt 粗体标题、正文 A、红色 IMAGE-1、粗体正文 B、两项原生项目列表、蓝色 IMAGE-2、正文 C。两张图片均为本次生成的测试图。

生成脚本及文件位于 `build/inline-image-probe/`（忽略目录）：`make.swift`、`NoteMenu-Inline-Probe.rtfd`、`IMAGE-1.png`、`IMAGE-2.png`。

在真实系统备忘录中分别执行：

1. 文件 → 导入至备忘录 → 选择 RTFD → 确认导入。
2. 文本编辑打开同一 RTFD，全选复制；备忘录中新建独立笔记，整体粘贴。

## 已验证结果

两种方式的备忘录正文均保持：正文 A → 图片 1 → 正文 B 与列表 → 图片 2 → 正文 C。原生辅助功能树识别两张内联图片，位置正确；粘贴结果截图确认红、蓝两张图片内容和顺序，未出现重复图片。标题的大小/粗体外观、正文粗体及两项列表可见；未验证标题是否转换为 Notes 原生标题语义。

测试笔记保留在本次新建的“导入的备忘录”文件夹中，共两条，标题均为“NoteMenu 独立图文顺序验证 0920”，创建时间分别为 20:11（导入）和 20:13（粘贴），可供人工复核。

## 接入边界

- 当前 `HTMLExporter.renderRuns` 过滤附件；`NotesSaver` 先创建全部文字，再追加图片，因此现有流程必然把图片放到末尾。模型中的位置仍完整保留。
- RTFD 可以承载顺序，备忘录导入与富文本粘贴也能保留顺序。“备忘录不能图文混排”不能作为绝对限制；现行限制属于当前保存通道。
- 本机 Notes 脚本字典提供正文 HTML 和附件操作，未见专门的 RTFD 导入命令。此次未验证通用 open 事件能否触发无交互导入，也未证明静默后台保存可行。
- 文件导入会出现选择与确认界面，并创建“导入的备忘录”文件夹，不能直接等同当前一键保存体验。
- 富文本粘贴可作为后续原型方向；产品接入仍需验证目标新笔记定位、焦点、剪贴板备份恢复、自动化权限、失败保留草稿以及保存完成判断。此次使用文本编辑的系统复制，尚未直接验证应用生成的剪贴板数据路径。
- 本次未覆盖全部格式、八级列表、超大图片、跨设备同步、重启持久性或连续高频保存，不能据此宣称完全兼容。

结论：按输入顺序保存图文已实机证明可行；保持现有静默后台保存体验仍需额外通道验证。正式替换保存实现前应先确定可接受的交互方式。

## 后台通道补充验证（取代上一阶段的待验证结论）

本轮通过 `osascript` 和与应用相同的 `NSAppleScript.executeAndReturnError` 实际调用 Notes；不用键盘模拟、不使用剪贴板，GUI 仅用于检查结果。测试均在独立文件夹“NoteMenu 后台通道验证 0920”中，共保留 9 条对照笔记。

| 路径 | 实测结果 |
| --- | --- |
| AppleScript `open POSIX file` 打开 RTFD | 能识别，但弹出“要导入至备忘录吗”确认框；已取消，不能直接静默保存 |
| 创建附件后把正文改成 `<img src="cid:…">` | 重写后附件数为 0，图片丢失 |
| HTML 内嵌 Base64 PNG | 两个位置保留，但显示为通用文件附件，不能作为正常图片方案 |
| Base64 加 `name=`、图片标签加 alt/title | 仍为无文件名附件，未解决 |
| HTML 引用此前已通过附件 API 交付的本地图片 URL | 正常显示两个图片，顺序正确；移走源文件后能导出，数据与原图逐字节一致 |
| 直接引用全新本地路径（原生调用，包含保留文件和唯一文件名对照） | 附件计数为 2，但导出失败 `-10000`；保留源文件并重试也未解决。因此不能把计数或命令返回当成保存完成，也不能仅归因于立即清理文件 |
| **原生调用：先创建附件，再以本地文件 URL 重写正文** | **成功：前台应用不变；图文顺序、粗体、列表正确；最终恰好两张图片；清理临时文件后仍能导出完整图片** |

成功原型步骤：

1. 为两张测试图生成唯一临时 PNG 路径。
2. 创建专用测试笔记，使用现有 `make new attachment ... with data (POSIX file ...)` 交付两张图片。
3. 对同一笔记设置完整 HTML，图片在原位置使用 `file://` URL；不使用 CID。
4. 从该笔记导出两张附件，校验数据与源图一致后，清理临时文件。此次第一次校验即通过，约 0.10 秒；这不是通用等待时长保证。
5. 清理后再次通过独立 AppleScript 导出，逐字节校验两张图仍与原图一致；正文读回包含两个有效图片标签，无 `(null)` 图片数据。
6. 最后才在 GUI 选中结果核对：A → 红图 → B 与列表 → 蓝图 → C，图片实际可见，未重复。

原生脚本调用前后记录的前台应用相同；创建与校验均未调用 activate/show 或任何 UI 操作。最终成功笔记标题为“NoteMenu NSAppleScript 先附件再混排验证”，创建时间 20:29。

证据位于 `build/inline-image-probe/`：`native-seeded.swift`、`native-seeded-result.txt`、`seeded-final.applescript`、`seeded-final-result.txt`、`seeded-final-1.png` 和 `seeded-final-2.png`。前面的失败对照及日志也保留在同目录。

根据对照，先通过附件 API 交付文件是当前已验证成功流程的必要步骤；可能涉及 Notes 对外部文件的访问或导入状态，但本轮没有证明内部原因。不能将单独 `<img src="file://…">` 的一次成功推广为任意新文件路径均可用。

**产品建议更新：继续使用 AppleScript 后台保存，采用“附件交付 → HTML 原位混排 → 确认附件完整 → 清理临时文件”的流程。无需为图文顺序改成 RTFD 导入或前台粘贴。** 这是独立可行性结论，正式接入仍需覆盖重复图片、任意文件名/路径、大图片、更多图片、保存中失败及重试、完整格式集合和不同系统版本；当前正式代码未变动。
